# AmneziaWG Web UI

Самостоятельно размещаемая веб-панель управления **AmneziaWG** —
обфусцированным, устойчивым к DPI форком WireGuard. Это один бинарник на
Go/Fiber: создавайте несколько серверов AmneziaWG, управляйте их клиентами
и следите за трафиком из одного веб-интерфейса, где **AmneziaWG 3.1
(header protection + random trailers) — встроенный и всегда включённый режим
обфускации**.

Вся настройка сервера выполняется через веб-интерфейс или REST API.
Переменные окружения при старте контейнера задают в основном лишь
*значения по умолчанию* — почти всё можно переопределить для каждого запроса
и каждого сервера через UI или API, кроме `WEB_UI_PORT`.

## 🔒 AmneziaWG 3.1 — главное

Это ключевая особенность проекта: **каждый созданный здесь сервер использует
полный набор параметров AmneziaWG 3.x** — устаревшего режима «базовой
обфускации» 1.0/1.5/2.0 больше нет, включать или выключать нечего, он
всегда активен.

AmneziaWG 3.0 добавляет **защиту заголовков (header protection)** поверх
обфускации мусорными пакетами и паддингом, которая была в предыдущих
поколениях AmneziaWG: 16-байтный заголовок пакета WireGuard (тип сообщения,
индекс получателя, счётчик) — та часть, что оставалась открытой даже при
обфускации 1.0/1.5/2.0 — шифруется ChaCha20 ключом (`HeaderProtectionKey`),
общим для сервера и клиента. Это убирает одну из последних
низкоэнтропийных, удобных для DPI сигнатур, которую оставляют в канале
протоколы на базе WireGuard.

Что приложение делает за вас автоматически:

*   Генерирует свежий случайный 32-байтный `HeaderProtectionKey` для каждого
    нового сервера (если вы не задали свой).
*   Соблюдает единственное жёсткое требование протокола: значения паддинга
    `S1`-`S4` должны быть **≥ 12 байт**, потому что 12-байтный nonce шифра
    защиты заголовков берётся из начала этого паддинга. Приложение проверяет
    это на стороне сервера и отказывается создавать сервер с нарушением.
*   Держит `HeaderProtectionKey` и все параметры обфускации
    синхронизированными между сервером и каждым сгенерированным клиентским
    конфигом — переносить их руками не нужно.
*   Включает оба переключателя формирования пакетов AmneziaWG 3.1,
    `RandomTrailers` и `DisableCookies`, для каждого нового сервера и
    записывает их в соответствующие клиентские конфиги (см. ниже — эти два
    параметра должны совпадать на обеих сторонах).
*   Даёт доступ к новым необязательным «клиентским» тайминг-параметрам
    AmneziaWG 3.0 (`ContentPaddingAddition`, `RekeyAfterTime`,
    `RekeyTimeout`, `RejectAfterTime`, `KeepaliveTimeout`,
    `MaxHandshakeAttempts`, `PersistentKeepalive`), чтобы вносить джиттер в
    тайминги рукопожатия и keepalive и в паддинг содержимого — иначе это
    постоянные и предсказуемые таймеры WireGuard. Полный справочник,
    значения движка по умолчанию и рекомендуемые диапазоны — в разделе
    [Параметры обфускации](#-параметры-обфускации).

### Что добавляет AmneziaWG 3.1

3.1 — небольшой дополняющий релиз поверх 3.0: два новых переключателя в
секции `[Interface]`, существующие параметры не менялись:

*   **`RandomTrailers`** — добавляет случайное число байт в конец каждого
    пакета, ориентируясь на «UDP-окно» пира, которое движок выводит из уже
    прошедшего трафика. Сообщения рукопожатия, длина которых была
    фиксированной и потому отпечатываемой даже в 3.0, больше не имеют
    постоянного размера в канале.
*   **`DisableCookies`** — интерфейс никогда не отвечает cookie reply и
    полностью пропускает проверку MAC2 под нагрузкой, так что обмен cookie
    исчезает как сигнатура (и как поверхность для отражённых атак).

**`RandomTrailers` — единственная настройка обфускации, которая обязана
совпадать на обеих сторонах.** Получатель принимает удлинённое рукопожатие
только если флаг включён у него самого, поэтому при несовпадении все
рукопожатия падают — молча, так как пакет просто не подходит ни под одну
известную форму и отбрасывается без записи в лог. `DisableCookies`, хотя и
идёт рядом, чисто локальный: движок читает его ровно в одном месте — в
ветке «под нагрузкой» на принимающей стороне, — поэтому его можно включить
на сервере, не трогая клиентов.

Приложение пишет оба флага из одних и тех же сохранённых значений в конфиг
сервера, в каждый клиентский `.conf` и в ссылку `vpn://`, так что они
остаются согласованными — но клиент старше AmneziaWG 3.1
(AmneziaVPN < 5.0.1.5) этих ключей вообще не знает. Снимите обе галочки в
форме создания сервера, если нужно поддержать такие клиенты. Существующих
серверов это не касается: в их сохранённых параметрах флагов нет, а
отсутствие флага означает «выключено».

## 🚀 Возможности

*   **Управление через веб**: понятный интерфейс для управления VPN-серверами и клиентами
*   **AmneziaWG 3.1 по умолчанию**: защита заголовков, random trailers, отключённые cookies, мусорные пакеты, паддинг сообщений и обфускация заголовков всегда полностью настроены — см. выше
*   **Управление клиентами**: генерация и скачивание клиентских конфигов, приостановка и повторная активация клиента на работающем сервере, автоматическая приостановка по времени
*   **Мониторинг**: статус сервера, трафик и подключения обновляются автоматически, опросом REST API
*   **Автозапуск**: автоматический старт серверов при перезапуске контейнера
*   **Автоматизация iptables**: настройка правил файрвола без ручной работы
*   **Свои значения**: MTU, подсеть, порт, DNS, endpoint и любой параметр обфускации AmneziaWG 3.x настраиваются для каждого сервера
*   **QR-код**: клиентский конфиг можно посмотреть, скопировать и скачать как текст, файл `.conf` или QR-код
*   **Нативная ссылка AmneziaVPN**: экспорт конфига клиента в виде ссылки `vpn://…`, которую официальное приложение распознаёт именно как AmneziaWG 3.x
*   **Просмотр конфигов**: конфиги и серверов, и клиентов открываются прямо из UI
*   **Данные клиента**: трафик, последнее рукопожатие и IP endpoint отображаются и автоматически обновляются

## 🏗️ Архитектура

### Компоненты

**Бэкенд на Go/Fiber** (`main.go`, `internal/`)

*   `main.go` — только сборка: читает окружение, поднимает менеджер,
    приложение Fiber, basic auth, REST-маршруты и отдачу фронтенда из
    `./web-ui/wasm`, слушает `WEB_UI_PORT`
*   `internal/httpapi` — обработчики маршрутов REST API: декодирование
    запросов и перевод типизированных ошибок менеджера в коды статуса. Сам
    не трогает ни диск, ни хост
*   `internal/manager` — бизнес-логика: жизненный цикл серверов и клиентов,
    приостановка, трафик, статус интерфейсов. Единственный владелец
    блокировки конфига; по файлам: `servers.go`, `clients.go`, `suspend.go`,
    `status.go`, `traffic.go`, `system.go`
*   `internal/awg` — единственное место, где вызывается shell: `awg`,
    `awg-quick`, `ip link`, скрипты iptables — за интерфейсом
    `Runner`, который тесты подменяют фейком из `awg/awgtest`
*   `internal/wgconf` — текст `.conf`: рендер `[Interface]` и клиентского
    конфига (один общий блок параметров AmneziaWG 3.x для обеих сторон),
    маркеры peer-блоков, приостановленные блоки, I1–I5 по умолчанию
*   `internal/amnezialink` — экспорт `vpn://` в нативном формате AmneziaVPN
*   `internal/store` — чтение/атомарная запись `web_config.json` и каркас
    однократных миграций схемы (`migrations.go`)
*   `internal/config` — переменные окружения → `Settings`; единственное
    место с `os.Getenv`
*   `internal/frontend` — отдача фронтенда с диска: gzip-бандл, ETag-валидаторы
    (чтобы браузер не крутил старый бандл после обновления и не качал заново
    ~50 МБ wasm при каждой загрузке), сжатие ответов
*   `internal/publicip`, `internal/netutil`, `internal/atomicfile` — мелкие
    вспомогательные пакеты: определение публичного адреса, арифметика
    подсетей, атомарная запись файлов
*   Ни reverse proxy, ни супервизора: единственный скомпилированный бинарник
    (`/usr/bin/api` в контейнере) делает всё, а
    [`tini`](https://github.com/krallin/tini) работает как PID 1 только для
    того, чтобы подбирать осиротевшие дочерние процессы

**Фронтенд на Fyne** (`web-ui/`, отдельный Go-модуль)

*   Приложение [Fyne](https://fyne.io), скомпилированное в WebAssembly — без
    JavaScript-фреймворков и без npm; `make web-ui` пакует его в
    `web-ui/wasm`, откуда сервер отдаёт файлы прямо с диска — в бинарник
    ничего не встраивается, поэтому бандл можно заменить без пересборки
    сервера
*   Единственная тёмная тема, принудительно заданная в самом приложении;
    страница загрузки — та, что генерирует `fyne package`, со стандартной
    тёмной стилизацией Fyne
*   Статус и трафик обновляются опросом REST: счётчики — раз в 5 секунд
    одним запросом `GET /api/traffic`, список серверов — раз в 30 секунд
    (и сразу после каждого действия из этой вкладки). Никаких сокетов: у
    wasm-сборки нет TCP-стека, а `fetch` браузер даёт бесплатно, вместе с
    учётными данными basic auth
*   В `web-ui/api` лежат все структуры запросов и ответов. Бэкенд
    импортирует тот же пакет через директиву `replace`, поэтому две стороны
    не могут разойтись
*   Правила AmneziaWG лежат в `web-ui/api` рядом с типами, к которым
    относятся: пределы, `Validate` для набора параметров обфускации,
    `ValidateCPS` для `I1`-`I5`, `GenerateObfuscation`. Форма и бэкенд
    вызывают одну и ту же копию, поэтому «форма пропустила, сервер отказал»
    невозможно; на бэкенде остались тонкие обёртки, сводящие список проблем к
    одной ошибке. В подписях полей — рекомендованные значения, в placeholder —
    допустимый диапазон

## 🔨 Сборка и локальный запуск

Нужен Go 1.26+. Бандл фронтенда собирается командой `make web-ui` (или
`make build`, которая сначала вызывает её) — инструмент упаковки `fyne`
объявлен как `tool`-зависимость модуля `web-ui`, поэтому отдельная установка
не требуется.

```bash
make help          # список всех целей с описаниями
make build         # make web-ui + go build -o server.bin . — сборка без docker
make build-server  # только бинарник; он отдаст бандл, уже лежащий в web-ui/wasm
make web-ui        # пересобрать только WebAssembly-бандл в web-ui/wasm
make vet           # go vet ./... по всем модулям (web-ui — под GOOS=js GOARCH=wasm, плюс e2e)
make run           # docker compose -f docker-compose.yml -f docker-compose.build.yml up --build
                   # собирает полный образ из исходников (бинарник Go + amneziawg-go + amneziawg-tools) и запускает его
make exec          # shell внутри работающего контейнера
make e2e           # поднять чистый тестовый экземпляр и прогнать браузерные тесты (playwright-go)
make profile-mem   # снять heap-профиль с работающего экземпляра и открыть в go tool pprof
make profile-cpu   # снять профиль CPU (30 с) и открыть в go tool pprof
make deploy        # собрать образ, выгрузить в proxy.tar и развернуть по ssh (хост спрашивается интерактивно)
```

`make run` — самый простой способ получить полностью рабочий контейнер (с
настоящим движком AmneziaWG в user space, умеющим v3), не устанавливая ничего,
кроме Docker. Настройки локального запуска лежат в `.env`
(`COMPOSE_PROJECT_NAME`, `AUTO_START_SERVERS`, `DEFAULT_MTU`, …); чего в нём
нет, берётся из значений по умолчанию — веб-интерфейс на `54845/tcp`, VPN на
`54844/udp`, пароль `changeme`. Настройки боевого стенда (свои порты и
`WEB_UI_PASSWORD`) лежат отдельно в `deploy/.env`: `make deploy` кладёт
именно его рядом с `docker-compose.yml` на сервере.

### Браузерные тесты

Фронтенд — это один канвас WebAssembly, поэтому селекторов CSS у него нет:
тесты в `e2e` кликают по координатам (при фиксированном окне 1500x950) и
проверяют результат через REST API, а скриншоты каждого шага складывают в
`e2e/shots/`. Написаны на Go через
[playwright-go](https://github.com/mxschmitt/playwright-go) и лежат в
отдельном модуле `e2e`, чтобы зависимость не попадала в основной `go.mod`.
Тесты делят один бэкенд и опираются на состояние друг друга (`02` создаёт
сервер, к которому `03` добавляет клиента), поэтому `go test` гоняет их по
порядку файлов в один поток, а рассчитывают они на экземпляр без настроенных
серверов. Node.js ставить не нужно: драйвер Playwright (вместе со своим
Node) `TestMain` при первом запуске скачивает в `~/.cache/ms-playwright-go`,
а браузер берётся установленный Chrome.

```bash
make e2e
```

`make e2e` сам приводит бэкенд в это состояние: `make e2e-reset` удаляет
контейнер и его volume, пересобирает образ, запускает его и ждёт ответа от
`/status`. Экземпляр намеренно отдельный от того, что оставляет `make run` —
свой контейнер `awgui-test`, свой volume `awgui-test-data`, порт `51836`, —
потому что сброс состояния перед тестами не должен трогать серверы, с
которыми вы работаете. После прогона он остаётся поднятым, чтобы можно было
посмотреть, на чём тест упал; `make e2e-down` убирает контейнер вместе с
volume.

Переопределяются они переменными Makefile: `E2E_PORT`, `E2E_NAME`,
`E2E_VOLUME`, `E2E_URL`, `E2E_TIMEOUT`, `E2E_TEST_TIMEOUT`. Прогнать тесты по уже работающему
экземпляру, ничего не пересоздавая, по-прежнему можно напрямую:

```bash
cd e2e && AWG_URL=http://localhost:54845 go test -count=1 -v .
```

## 🔧 Эндпоинты API

Все маршруты, кроме `/status`, закрыты basic auth (см. [Безопасность](#безопасность)).

### Управление серверами

#### Создать сервер

```yaml
POST /api/servers
Content-Type: application/json

{
  "name": "My VPN Server",
  "port": 54844,
  "subnet": "10.0.0.0/24",
  "mtu": 1280,
  "endpoint": "vpn.example.com",
  "dns": "8.8.8.8,1.1.1.1",
  "obfuscation": true,
  "auto_start": true,
  "obfuscation_params": {
    "Jc": 8,
    "Jmin": 8,
    "Jmax": 80,
    "S1": 50,
    "S2": 60,
    "S3": 20,
    "S4": 16,
    "H1": 1000,
    "H2": 2000,
    "H3": 3000,
    "H4": 4000,
    "MTU": 1280
  }
}
```

`endpoint` и `dns` необязательны: без них берётся определённый публичный IP
и `DEFAULT_DNS`. `dns` принимает как строку через запятую, так и массив строк.

#### AmneziaWG 3.1 (защита заголовков, random trailers)

Режим обфускации теперь только один: `"obfuscation": true` всегда включает
полный набор параметров AmneziaWG 3.x, включая обязательную защиту
заголовков. Старые режимы только-1.0/1.5/2.0 (и прежние флаги запроса
`awg2`/`awg3`) удалены.

*   `S1`, `S2`, `S3`, `S4` должны быть **≥ 12** (шифр защиты заголовков берёт
    свой 12-байтный nonce из начала этого паддинга); иначе сервер отклонит
    запрос. Документация рекомендует задавать все четыре одинаковыми, а
    `H1`-`H4` оставлять равными 1/2/3/4 — подробнее в разделе
    [Параметры обфускации](#-параметры-обфускации).
*   Требуется 32-байтный `HeaderProtectionKey` в base64; он генерируется
    автоматически, если вы не передали свой в `obfuscation_params`. Он должен
    побайтово совпадать у сервера и каждого его клиента — для конфигов,
    которые генерирует приложение, это делается автоматически.
*   Необязательные «клиентские» тайминг-параметры (каждая сторона применяет
    их к собственному поведению, поэтому совпадать они не обязаны):
    `ContentPaddingAddition`, `RekeyAfterTime`, `RekeyTimeout`,
    `RejectAfterTime`, `KeepaliveTimeout`, `MaxHandshakeAttempts`,
    `PersistentKeepalive`. Каждый принимает целое число или диапазон
    `"a-b"` (например, `"5-10"`); оставьте пустым, чтобы использовать
    значения движка по умолчанию.

    Каждый из них хранится в `awg(8)` как пара `uint16`, поэтому обе границы
    диапазона должны укладываться в `0-65535`, а вторая — быть не меньше
    первой; это записано в подписях полей формы и проверяется и на клиенте, и
    на сервере.

    | Параметр | Значение движка (не задано) | Рекомендуемый диапазон |
    |---|---|---|
    | `ContentPaddingAddition` | выкл. (выравнивание по 16 байт) | `0-64` |
    | `RekeyAfterTime` | 120 с | `100-140` |
    | `RekeyTimeout` | 5 с | `4-7` |
    | `RejectAfterTime` | 180 с | `160-200` |
    | `KeepaliveTimeout` | 10 с | `8-12` |
    | `MaxHandshakeAttempts` | 18 | `14-20` |
    | `PersistentKeepalive` | 25 с | `22-30` (из примера в README самого `amneziawg-go`) |

    Столбец «значение движка» взят напрямую из `device/constants.go`
    в `amneziawg-go` (стандартные тайминговые константы WireGuard).
    Официально задокументированный рекомендуемый диапазон есть только у `Jc`
    (`4-12`) и `PersistentKeepalive` (`22-30`) — остальная часть столбца
    «рекомендуемый диапазон» это консервативный джиттер вокруг значений по
    умолчанию, а не официальная рекомендация: AmneziaWG её не публикует.

*   Два переключателя формирования пакетов AmneziaWG 3.1, `RandomTrailers` и
    `DisableCookies` — обычные булевы значения JSON, оба **включены**, когда
    сервер генерирует параметры сам:

    | Параметр | Тип | По умолчанию | Примечания |
    |---|---|---|---|
    | `RandomTrailers` | bool | `true` | Случайный «хвост» у каждого пакета; **должен совпадать на сервере и клиенте** |
    | `DisableCookies` | bool | `true` | Никогда не отправлять cookie reply, пропускать проверки MAC2 под нагрузкой |

    Передайте `"RandomTrailers": false` (и/или `"DisableCookies": false`) в
    `obfuscation_params`, чтобы их не включать. Выключенный флаг пишется как
    *полное отсутствие строки*, а не `= off`, потому что парсер до 3.1
    отвергает неизвестный ключ целиком и отказался бы импортировать конфиг.

```yaml
POST /api/servers
Content-Type: application/json

{
  "name": "My VPN Server (AWG 3.1)",
  "port": 54844,
  "subnet": "10.0.1.0/24",
  "mtu": 1280,
  "obfuscation": true,
  "obfuscation_params": {
    "Jc": 8, "Jmin": 8, "Jmax": 80,
    "S1": 50, "S2": 66, "S3": 20, "S4": 16,
    "H1": 1000, "H2": 2000, "H3": 3000, "H4": 4000,
    "MTU": 1280,
    "ContentPaddingAddition": "0-64",
    "RekeyAfterTime": "100-140",
    "PersistentKeepalive": "22-30",
    "RandomTrailers": true,
    "DisableCookies": true
  }
}
```

> [!NOTE]
> **Перенос уже работающего сервера**: существующие серверы продолжают
> работать без изменений — это касается только вновь создаваемых. Пересоберите
> образ (`docker compose build` / `make run`), чтобы получить закреплённые
> бинарники `amneziawg-go`/`amneziawg-tools` версии 3.1; новый движок читает
> конфиг эпохи 3.0 ровно так же, как раньше, а отсутствующие ключи
> `RandomTrailers`/`DisableCookies` означают «выключено». Серверы, созданные
> до появления поддержки AmneziaWG 3.0 (без `HeaderProtectionKey` и,
> возможно, с `S1`-`S4` меньше 12), тоже работают как прежде — их файлы
> конфигурации ничто автоматически не переписывает. Чтобы перевести такой
> сервер на AmneziaWG 3.x, его нужно пересоздать (либо вручную отредактировать
> `web_config.json` и `.conf` сервера, добавив `S1`-`S4` ≥ 12 и
> `HeaderProtectionKey`), а затем раздать заново сгенерированные клиентские
> конфиги — старые конфиги без совпадающего `HeaderProtectionKey` не смогут
> подключиться, как только на сервере включится защита заголовков.

{

  "server_traffic": {
    "<server_id>": { "rx": "1.20 MB", "tx": "3.40 MB", "rx_bytes": 1258291, "tx_bytes": 3565158, "uptime_seconds": 4215 }
  },

соседних ответов панель считает скорость и загрузку CPU. Байты сервера и
клиентов — из одного источника, `awg show <iface> transfer`: сервер — сумма
по своим пирам, так что его цифра всегда равна сумме строк клиентов (пиры,
вписанные в `.conf` мимо панели, входят в сумму, но строки не получают). Историю за 5 минут
хранит только страница; сервер между запросами ничего не запоминает.
`storage` — файловая система тома `/etc/amnezia`, `memory` — как у `free`
(занято = всего − доступно). Показание, которое не удалось снять, приходит
нулями.

## 📈 Профилирование

Сервер умеет отдавать профили `net/http/pprof`, но только если запущен с
`WEB_UI_PPROF=1`: сбор профиля CPU отнимает у работающего сервера реальное
время, а сами эндпоинты выдают стеки горутин и командную строку процесса.
Маршруты подключаются **после** basic auth, поэтому `/debug/pprof` требует
те же учётные данные, что и API.

```bash
# docker compose: добавьте переменную в .env (или в environment сервиса)
echo 'WEB_UI_PPROF=1' >> .env && docker compose up -d
```

Дальше профиль снимается целями Makefile — они скачивают его в `profiles/`
(каталог в `.gitignore`) и открывают в `go tool pprof`:

```bash
make profile-mem                      # текущая куча (inuse_space), со сборкой мусора перед снимком
make profile-alloc                    # всё, что аллоцировалось с момента старта (alloc_space)
make profile-cpu                      # 30 секунд CPU; нагрузите сервер, пока идёт сбор
make profile-cpu PPROF_SECONDS=60     # другая длительность
make profile-clean                    # удалить скачанные профили
```

Каждый снимок кладётся под своим таймстампом (`heap-20260903-141500.pprof`),
поэтому два последних — это пара «до/после». Сравнить их:

```bash
make profile-diff                     # два последних heap-профиля
make profile-diff PPROF_KIND=cpu      # два последних CPU-профиля
make profile-diff PPROF_KIND=alloc    # два последних alloc-профиля
```

`profile-diff` вычитает старший снимок из младшего (`go tool pprof -base`) и
показывает только то, что изменилось: рост между двумя снимками кучи после
GC — признак утечки, а падение после правки — подтверждение, что она
сработала. Сравнение работает и между разными бинарниками: сэмплы
сопоставляются по именам функций, а не по адресам.

Настройки переопределяются переменными make:

| Переменная | По умолчанию | Описание |
|----------|---------|-------------|
| `PPROF_HOST` | `localhost` | Хост работающего экземпляра |
| `PPROF_PORT` | `54845` | Порт (`WEB_UI_PORT` этого экземпляра) |
| `PPROF_USER` | `admin` | Пользователь basic auth |
| `PPROF_PASSWORD` | `changeme` | Пароль **открытым текстом**, а не хеш из `WEB_UI_PASSWORD` |
| `PPROF_SECONDS` | `30` | Длительность сбора профиля CPU |
| `PPROF_DIR` | `profiles` | Куда складываются скачанные профили |
| `PPROF_KIND` | `heap` | Что сравнивает `profile-diff`: `heap`, `cpu` или `alloc` |
| `PPROF_FLAGS` | — | Дополнительные флаги `go tool pprof`: `-http=:8081` откроет веб-интерфейс (нужен graphviz), `-top -nodecount=20` просто напечатает горячие места |

```bash
make profile-mem PPROF_PASSWORD=secret PPROF_FLAGS=-http=:8081
```

Остальные профили (`goroutine`, `allocs`, `block`, `mutex`, `trace`) доступны
по тем же адресам вручную; индекс со списком — `GET /debug/pprof/`. Учтите,
что `block` и `mutex` без `runtime.SetBlockProfileRate` / `SetMutexProfileFraction`
всегда пустые.

## 🐳 Развёртывание в Docker

CI собирает и публикует образ в Docker Hub при каждом push в `master` и по
тегам (см. `.github/workflows/docker.yaml`); точный тег смотрите в Docker Hub
своего форка (`docker.io/<ваш-логин-dockerhub>/<имя-репозитория>`) либо просто
соберите локально через `make run` / `docker compose build`.

Образ весит всего **~26 МБ**: ни интерпретаторов, ни nginx, ни supervisor.
Для сравнения, [`ghcr.io/w0rng/amnezia-wg-easy:latest`](https://github.com/w0rng/amnezia-wg-easy)
весит ~80 МБ.

Версии upstream AmneziaWG закреплены в `Dockerfile`
(`AWG_GO_VERSION=v3.1.20260828`, `AWG_TOOLS_VERSION=v3.1.20260812`), поэтому
пересборка не может незаметно подтянуть несовместимый или сломанный коммит
из `master`. Обе версии должны быть из одного поколения AmneziaWG. Собрать с
другими тегами:

```bash
docker build --build-arg AWG_GO_VERSION=vX.Y.Z --build-arg AWG_TOOLS_VERSION=vX.Y.Z -t awgui .
```

### Пример docker compose

В репозитории уже есть два compose-файла: `docker-compose.yml` (базовый,
запускает готовый `image:`, без сборки) и `docker-compose.build.yml`
(оверлей, добавляющий `build: .`). `make run` объединяет оба, чтобы собрать
из исходников и запустить; чтобы поднять уже собранный или скачанный образ,
используйте только базовый файл: `docker compose -f docker-compose.yml up -d`.
Базовый файл читает порты и настройки из `.env`; если переменных там нет,
подставляются те же значения по умолчанию, что и в образе — `54845/tcp` для
веб-интерфейса и `54844/udp` для VPN.

Самостоятельный `docker-compose.yml` для VPS с готовым образом из Docker Hub
(тот же, что в README):

```yaml
services:
  app:
    image: myceliummesh/amneziawg-ui:latest
    restart: unless-stopped
    ports:
      - "54845:54845/tcp"   # веб-интерфейс
      - "54844:54844/udp"   # VPN (Можно задать диапазон)
    environment:
      - WEB_UI_USER=admin
      # base64(sha256(пароль)); значение ниже — это "changeme", замените:
      # printf 'ваш-пароль' | openssl dgst -binary -sha256 | base64
      - WEB_UI_PASSWORD=BXugPWxEEEhj3HNh/kV4ll0YhzYPkKCJWILlimJI/IY=
    volumes:
      - data:/etc/amnezia
    cap_add:
      - NET_ADMIN
      - SYS_MODULE
    devices:
      - /dev/net/tun
    sysctls:
      - net.ipv4.ip_forward=1
      - net.ipv4.conf.all.src_valid_mark=1
      - net.ipv6.conf.all.disable_ipv6=0
      - net.ipv6.conf.all.forwarding=1
      - net.ipv6.conf.default.forwarding=1
    logging:
      options:
        max-size: 10m
        max-file: 3

volumes:
  data:
```

```sh
docker compose up -d
```

Другие порты и настройки по умолчанию задаются через `environment` теми же
переменными из таблицы выше; при смене `WEB_UI_PORT` или `DEFAULT_PORT` не
забудьте поправить и `ports`.

Если нужен HTTPS, поставьте перед контейнером собственный reverse proxy с
терминацией TLS (nginx, Caddy, Traefik и т. п.) и проксируйте на `WEB_UI_PORT`.

## 📊 Параметры обфускации

Каждый созданный здесь сервер использует полный набор параметров обфускации
AmneziaWG 3.x (параметры, относящиеся к защите заголовков, два переключателя
3.1, значения движка по умолчанию и рекомендуемые диапазоны необязательных
тайминг-параметров см. выше в разделе
[AmneziaWG 3.1 — главное](#-amneziawg-31--главное)). Этот раздел описывает
базовые параметры мусорных пакетов, паддинга и заголовков, общие с
предыдущими поколениями AmneziaWG.

### Справочник параметров

Колонка «допустимо» — это то, что примет движок (и что проверяет приложение);
«рекомендуется» — то, что советует документация AmneziaWG. Именно
рекомендуемые значения стоят в подписях полей формы, а допустимый диапазон —
в placeholder.

Две строки таблицы условны. Совет по `H1`-`H4` относится к защите заголовков,
а она в этом приложении включена всегда, так что выполняется безусловно. Совет
задавать все четыре `S` одинаковыми относится к `RandomTrailers` — это
включённая по умолчанию галочка, и если её снять, он перестаёт действовать.

| Параметр | Допустимо | Рекомендуется | Описание |
| --- | --- | --- | --- |
| `Jc` | 0-65535 | 4-12 | Количество мусорных пакетов перед рукопожатием |
| `Jmin` | 1-65535, < `Jmax` | 8 | Минимальный размер мусорного пакета |
| `Jmax` | 1-65535, > `Jmin`, ≤ MTU | 80 | Максимальный размер мусорного пакета |
| `S1` | 12-65535, ≤ MTU-148, `S1+56 ≠ S2` | 15-150 | Паддинг перед сообщением handshake initiation |
| `S2` | 12-65535, ≤ MTU-92 | как `S1` | Паддинг перед сообщением handshake response |
| `S3` | 12-65535 | как `S1` | Паддинг перед сообщением cookie reply |
| `S4` | 12-65535 | как `S1` | Паддинг перед каждым транспортным сообщением (данные) |
| `H1`-`H4` | Уникальные, 1-4294967295 | 1/2/3/4 | Значения поля типа сообщения для handshake-init/response/cookie/transport |
| `HeaderProtectionKey` | 32 байта в base64 | генерируется автоматически | Ключ защиты заголовков AmneziaWG 3.0, должен совпадать на сервере и клиенте |
| `RandomTrailers` | bool | `true` | AmneziaWG 3.1: случайный «хвост» у каждого пакета, должен совпадать на сервере и клиенте |
| `DisableCookies` | bool | `true` | AmneziaWG 3.1: никогда не отправлять cookie reply, пропускать проверки MAC2 под нагрузкой |
| `MTU` | 1280-1440 | 1280 | MTU интерфейса туннеля |

Границы `S1`/`S2` зависят от MTU (`S1 ≤ MTU-148`, `S2 ≤ MTU-92`, обе не
больше 150); приложение проверяет это, а также правила `S1+56 ≠ S2` и
`S3`/`S4` ≥ 12 и на клиенте (валидация формы), и на сервере — до записи
любого файла конфигурации.

Типы взяты из
[справочника параметров AmneziaWG 3.1](https://docs.amnezia.org/documentation/amnezia-wg/):
`Jc`, `Jmin`, `Jmax` и `S1`-`S4` — `uint16`; `H1`-`H4` — диапазоны `uint32`,
которые не должны пересекаться между собой (`mergeWithDevice` в `amneziawg-go`
отвергает пересечение); тайминг-параметры и `ContentPaddingAddition` —
диапазоны `uint16`. Рекомендации по `Jc`, `Jmin`, `Jmax`, `S1` и `S2` — из
[README amneziawg-linux-kernel-module](https://github.com/amnezia-vpn/amneziawg-linux-kernel-module).

Две рекомендации относятся именно к режиму AmneziaWG 3.1 и объясняют колонку
«рекомендуется»:

*   **Все четыре паддинга одинаковы — пока включён `RandomTrailers`.**
    «When using `RandomTrailers`, it is recommended to set the same values for
    `S1`, `S2`, `S3` and `S4`» — случайные «хвосты» делают размеры пакетов
    плавающими, и одинаковые `S` не дают принять один тип сообщения за другой.
    Со снятой галочкой этого требования нет.

    У этого совета есть цена, о которой документация не пишет: при равных `S`
    разница между минимальными размерами типов сообщений остаётся ровно
    штатной для WireGuard (148/92/64/32), и наблюдатель, набравший минимумы,
    восстанавливает эту структуру. Разные `S` её маскируют, но лишают приёмник
    того самого запаса. Выбор вынесен галочкой «Roll S1-S4 separately» в
    расширенном режиме; по умолчанию и в упрощённом режиме — как рекомендует
    вендор.
*   **`H1`-`H4` остаются равны 1/2/3/4.** «When using Header Protection, it is
    recommended to leave `H1`-`H4` at the standard compatibility values… In
    this mode, the custom header mechanism is disabled, and the message type
    is hidden by Header Protection». Защита заголовков шифрует само поле типа
    сообщения, поэтому подменять его дополнительно незачем. Совет «уникальные
    значения из 5-2147483647» относится к AmneziaWG без защиты заголовков.

Приложение генерирует параметры именно в этой форме, но не запрещает
отступать от неё: проверка отвергает только то, что отвергнет сам движок.

### Подробное описание параметров

#### Jc, Jmin, Jmax (мусорные пакеты)

*   Отправляются непосредственно перед каждой попыткой рукопожатия, чтобы
    сломать фиксированную сигнатуру рукопожатия WireGuard из двух датаграмм.
*   Меньше `Jc` — меньше мусорных пакетов (выше производительность, слабее
    обфускация); больше `Jc` — больше мусорных пакетов (сильнее обфускация,
    чуть больше накладных расходов). Обычно рекомендуют диапазон 4-12.

#### S1-S4 (паддинг сообщений)

*   `S1`/`S2` дополняют сообщения handshake initiation/response; `S3`/`S4` —
    cookie reply и транспортные сообщения.
*   Поскольку защита заголовков AmneziaWG 3.0 берёт 12-байтный nonce шифра из
    начала этого паддинга, **все четыре должны быть ≥ 12**, когда задан
    `HeaderProtectionKey` (а это приложение задаёт его всегда).
*   С включённым `RandomTrailers` (галочка по умолчанию, но её можно снять)
    документация рекомендует задавать все четыре **одинаковыми**: размеры
    пакетов и так плавают из-за случайного «хвоста», а разные `S` повышают
    риск принять один тип сообщения за другой.

#### I1-I5 (сигнатурные пакеты, CPS)

*   Отправляются перед каждым рукопожатием, в порядке `I1`…`I5`, ещё до
    мусорных пакетов `Jc`. Незаданные пропускаются; если не задан ни один,
    CPS-пакеты не отправляются вовсе. В этом приложении пустой `I1`
    отключает весь набор.
*   Значение — не число, а описание пакета байт за байтом в формате **CPS**
    (Custom Protocol Signature): последовательность тегов.

    | Тег | Что кладёт | Ограничение |
    |---|---|---|
    | `<b 0x…>` | статические байты — имитация реального протокола | hex, **чётное** число символов; префикс `0x` необязателен |
    | `<t>` | Unix-время, 4 байта, network byte order | без аргумента |
    | `<r N>` | N криптослучайных байт | N ≤ 1000 |
    | `<rc N>` | N случайных букв `[a-zA-Z]` | N ≤ 1000 |
    | `<rd N>` | N случайных цифр `[0-9]` | N ≤ 1000 |

    Пример: `<b 0xd100000001><rc 8><t><r 50>`. Текст вне тегов движок
    игнорирует.
*   Приложение разбирает значение по тем же правилам, что и `newObfChain` в
    `amneziawg-go` — и в форме, и на сервере, до записи конфига. Строже
    движка оно ровно в одном месте: непустое значение вообще без тегов
    upstream принимает и молча не шлёт никакого пакета, а это может быть
    только опечаткой.
*   Размер пакета ограничен не тегами, а путём: «If the final size of any
    packet exceeds system MTU, it would be fractured into fragments, which
    looks suspicious». Держите его примерно до 1472 байт. Дефолтный `I1` в
    поставке — статические 1200 байт.
*   **Это параметры одной стороны, а не пары.** Их шлёт только тот, кто
    инициирует рукопожатие, поэтому в конфиг сервера они не пишутся никогда —
    только в клиентские конфиги и в ссылку `vpn://`. Рекомендация upstream:
    «no need to specify it on both sides… use it on the client side only».
*   Хранятся **у каждого клиента отдельно** (`apply_i_settings` +
    `i_settings`). Общий для сервера набор по умолчанию отдаётся в
    `GET /api/default-i-settings` и берётся за основу при создании клиента с
    включённым `apply_i_settings`; введённые вручную непустые значения
    перекрывают его по ключам.

#### H1-H4 (значения заголовков)

*   Заменяют поле типа сообщения у каждого типа пакета, чтобы он не выглядел
    узнаваемой сигнатурой WireGuard/AmneziaWG. Все четыре должны отличаться
    друг от друга.
*   Значения 1/2/3/4 — обычные типы сообщений WireGuard: для AmneziaWG это
    означает «подмена заголовков выключена». С защитой заголовков документация
    рекомендует именно их, потому что поле типа шифруется и без подмены.
    Уникальные значения из 5-2147483647 — совет для AmneziaWG **без** защиты
    заголовков; приложение их принимает, но само не генерирует.
*   На стойкость к DPI выбор здесь не влияет вообще. Паддинг `S` заполняется
    `rand.Read` на каждый пакет, его первые 12 байт — nonce ChaCha20, и
    `cip.XORKeyStream` накрывает у рукопожатий весь пакет, у транспортных —
    16-байтный заголовок. Значение `H` в открытом виде на провод не попадает,
    поэтому `1` и `868561` для наблюдателя одинаково неразличимы.

#### MTU

*   `1280` — самое безопасное и совместимое значение; `1420`-`1440` даёт
    лучшую пропускную способность, но в некоторых сетях приводит к
    фрагментации.
*   Упрощённый режим формы берёт MTU из `DEFAULT_MTU`, с которым запущен
    бэкенд (значение приезжает во фронтенд в `/api/system/status`), а не из
    зашитой константы. Расширенный режим подставляет его же в поле при
    открытии формы, пока вы не вписали туда своё.
*   С AmneziaWG 3.x это уже не просто «в некоторых сетях»: паддинг `S4`
    добавляется к **каждому** транспортному пакету, а он обязан быть ≥ 12.
    Полноразмерный пакет в канале весит `MTU + 32` (заголовок и тег
    WireGuard) `+ 28` (IPv4/UDP) `+ S4`, так что при обычном пути в 1500 байт
    на паддинг остаётся `1440 − MTU`: при MTU 1280 это 160 (весь
    рекомендованный диапазон 15-150 помещается), при 1420 — всего 20, а при
    1440 не остаётся ничего и фрагментация неизбежна. Генератор учитывает это
    и сужает окно паддинга под выбранный MTU.

## 📝 Логи и мониторинг

### Логи приложения

Приложение пишет только в stdout/stderr (стандартная практика для
контейнеров), смотреть так:

`docker logs -f amnezia-web-ui`

Базовый `docker-compose.yml` ограничивает журнал тремя файлами по 10 МБ.

## 🔄 Резервное копирование и восстановление

Отдельного эндпоинта экспорта/импорта нет — сохраняйте целиком каталог
состояния AmneziaWG: в нём лежит `web_config.json` (метаданные серверов и
клиентов, ключи, все параметры AmneziaWG 3.x) и файл `.conf` каждого
интерфейса:

```bash
docker cp amnezia-web-ui:/etc/amnezia ./amnezia-backup/
```

Для восстановления остановите контейнер, скопируйте сохранённый каталог
обратно в том `/etc/amnezia` и запустите контейнер снова.

Отдельный сервер или клиента можно также просто скачать через UI или
`GET /api/servers/{server_id}/config` /
`GET /api/servers/{server_id}/clients/{client_id}/config`.

# Безопасность

Приложение выставлено напрямую на порт 80 (или заданный `WEB_UI_PORT`), с
basic-аутентификацией, встроенной в само приложение Fiber. Без авторизации
доступен только `/status` — health check контейнера; вся статика UI закрыта
теми же учётными данными, что и API.

> [!IMPORTANT]
> Настоятельно рекомендую закрывать эндпоинты файрволом и/или reverse proxy с
> терминацией TLS перед контейнером.
> Одной basic-аутентификации недостаточно, её можно подобрать перебором.

По умолчанию образ собирается с пользователем `admin` и паролем `changeme`.
Чтобы изменить это, передайте переменные окружения Docker `WEB_UI_USER` и
`WEB_UI_PASSWORD` (пароль — SHA-256 в base64, см. таблицу выше).
